# REACT_DEVELOPMENT_RULES.md — 高信頼Reactアプリ開発規約

版: 1.0.0 / 作成日: 2026-11-15

## 1. 目的と適用範囲

Reactアプリケーションの要件整理、設計、実装、テスト、独立レビュー、改善、納品に適用する。見た目だけの完成ではなく、実データによる主要操作、保存・復元、失敗時の回復までを検証する。

本書はReact開発の追加規約であり、既存のORCHESTRATOR.md、AGENTS.md、REVIEWER.mdを置き換えない。Pythonバックエンドには既存のPython開発規約も適用する。第14章はShorts管理などのメディア編集機能がある場合に適用する。

「必須」は遵守事項、「推奨」は理由を記録して変更可能な方針、「例」は採用を強制しない構成を意味する。本書の技術選定はプロジェクト方針であり、React公式の必須条件ではない。

## 2. 作業開始と規約の優先順位

1. ユーザーの目的、対象OS・ブラウザ、配布方式、既存コード、実行環境を確認する。
2. 本書とORCHESTRATOR.md、AGENTS.md、REVIEWER.mdの利用可能な最新版を読む。内容を確認できない文書を推測で適用しない。不足と実行可能な範囲を報告する。
3. 上位の実行環境指示、ユーザーの明示的要求、適用されるプロジェクト規約の順で判断する。同順位の重要な矛盾は解消してから依存作業を行う。
4. スコープ、受け入れ条件、変更対象、検証方法を定める。通常の実装判断は自律的に進める。
5. 大幅な仕様解釈の分岐、データ削除、重大な権限変更、課金などは既存の承認範囲を確認し、必要な場合のみ判断を求める。

規約を置くだけで自動読込が保証されるとは扱わない。プロジェクトの入口文書から本書への参照を設定し、作業時に読込状況を明示できるようにする。

## 3. 役割と開発サイクル

| 役割 | 責務 |
| --- | --- |
| Orchestrator | 要件・完了条件、担当、依存関係、進捗、重大指摘の解消、最終報告 |
| Developer | 調査、設計、実装、自己テスト、変更根拠と検証記録 |
| Independent Reviewer | 要件・実コード・差分・ログから独立検証し、重大度付きで報告 |

利用可能な委任機能と適用指示に従い、実装と独立レビューの担当を分ける。利用できない場合は役割を分離した逐次実行で代替し、独立した別エージェントによるレビューではないことを報告する。役割名だけで並列実行や独立性を主張しない。

標準工程は「要件整理 → 現状調査 → 設計 → 実装 → 自己テスト → 独立レビュー → 修正・再検証 → 納品」とする。軽微な変更は簡略化できるが、変更に見合う確認は行う。

## 4. 技術選定・依存関係

- 新規の操作主体のローカルWeb UIはReact＋TypeScriptを推奨する。ビルド環境はViteなどから要件に合わせて選ぶ。SSRなどが必要な場合は別途評価する。
- React、Node.js、TypeScript、パッケージマネージャー、対象ブラウザ、Python連携時のPython・FFmpegの採用バージョンをREADMEに記録する。「最新版」という記載だけで済ませない。
- 既存プロジェクトの構成とロックファイルを優先し、理由なくフレームワークやパッケージマネージャーを変更しない。
- 新規ライブラリは必要性、互換性、ライセンス、保守状況を一次情報で確認する。実装時点の情報を用い、未確認のAPIやバージョンを前提にしない。
- 使用するパッケージマネージャーとロックファイルを統一し、再現可能なインストール手順を用意する。
- 型検査、lint、テスト、ビルドのスクリプトを明示する。ビルドが型検査を含むか確認し、含まない場合は別コマンドで実行する。
- UI、状態管理、HTTP通信のライブラリは必要に応じて追加する。単純な処理に大規模な依存関係を導入しない。

## 5. 構成と責務分離

画面描画、編集ルール、外部通信、永続化を分離する。ReactコンポーネントからDBやFFmpegを直接操作しない。既存PythonロジックはUI依存を調査してからサービス経由で再利用する。

新規構成の例:

```text
frontend/
  src/
    app/          # 起動、ルーティング、共通設定
    features/     # 楽曲管理、編集、書き出し等の機能単位
    components/   # 共通UI部品
    services/     # APIクライアント、通信契約
    lib/          # 汎用処理
    styles/       # デザイントークン、共通スタイル
  e2e/            # 主要操作のブラウザテスト
backend/          # Python連携がある場合
docs/             # 設計・API契約・検証記録
```

ディレクトリは必要な時点で作成する。既存構成の全面置換や、使われない抽象化を行わない。

## 6. React・TypeScript実装

- 新規TypeScript設定ではstrictを有効にする。既存への導入は影響を評価して段階化できる。
- Props、API入出力、主要なドメインデータを型定義する。外部入力は実行時にも検証し、型アサーションだけで安全とみなさない。
- any、非nullアサーション、型検査抑制は常用しない。必要時は理由と適用範囲を限定する。
- 関数コンポーネントを基本とし、コンポーネントは役割が明確な単位に分割する。行数だけを基準に分割しない。
- レンダリング中に外部書き込みや副作用を起こさない。Hooksの呼出順序を守り、依存関係の警告を根拠なく抑制しない。
- useEffectは外部システムとの同期に用いる。算出可能な値は原則としてレンダリング中に算出し、ユーザー操作の処理はイベントハンドラーに置く。
- Effectで登録した購読、イベント、タイマー、接続は解除する。再実行による二重登録を防ぐ。
- 配列のkeyは安定したIDを使う。並べ替え・削除がある一覧で位置だけを識別子にしない。
- 状態を直接変更しない。関連状態の遷移が複雑ならReducer等で整理する。
- Strict Modeは新規開発で推奨する。問題を隠すための無効化を避け、開発時の再実行にも耐える処理にする。
- memo、useMemo、useCallbackは計測または明確な必要性に基づいて使う。

## 7. 状態管理・非同期処理

状態を「一時UI状態」「編集中のドメイン状態」「サーバーの永続データ」「再計算可能な値」に分け、正本と更新経路を定める。

- 共有不要な状態は局所化する。Contextや外部ストアへの一括集約を避ける。
- 読込中、空、成功、失敗、保存中、未保存を区別して表示する。
- 曲や画面の切替後に古いレスポンスが新しい状態を上書きしないよう、キャンセルまたはリクエスト識別で防ぐ。
- AbortController等による通信中止と、サーバー上の実ジョブ中止を区別する。
- 保存・書き出しの連打を防ぎ、必要に応じてサーバーでも冪等性を確保する。
- 自動保存は頻度を制御し、保存成功の応答前に「保存済み」と表示しない。保存競合は版番号などで検出し、古い変更の上書きを防ぐ。
- 通信失敗時は編集内容を維持し、再試行と回復方法を示す。再試行が重複処理を起こさない設計とする。
- 編集プロジェクトは永続化し、再起動後に復元できることを確認する。localStorageのみを長期保存の前提にしない。

## 8. UI・アクセシビリティ

- 主要操作と情報の優先順位を明確にし、余白、色、文字、状態表示を統一する。デザイントークンで共通化する。
- 日本語ラベルを基本とし、処理失敗は原因と対処を示す。技術用語や内部例外をそのまま主要導線に表示しない。
- ボタンや入力は適切なHTML要素で実装する。入力ラベル、キーボード操作、フォーカス表示、ダイアログのフォーカス管理を確認する。
- 色だけで状態を表さない。アイコン操作には読み上げ可能な名前を付ける。
- ドラッグ操作には数値入力やキーボードなどの代替操作を用意する。
- 対象画面サイズ、表示倍率、長い曲名・日本語・大量データで切れや重なりを確認する。モバイル対応は要件に含まれる場合に検証する。
- 破壊的操作は影響を示し、元に戻す・バックアップ・確認などを影響度に応じて設計する。
- デザイン画像は参考とし、実装済み・操作可能とは報告しない。モックと実API接続を明確に分ける。

## 9. Python・API連携

- ローカル構成の例はReact UI＋FastAPI等のAPI＋既存Python処理＋SQLiteである。採用は要件と既存コードに基づく。
- URL、HTTPメソッド、入出力、単位、必須項目、エラー形式を契約として記録する。API契約と型定義の不整合を検出する。
- APIクライアントを集約し、タイムアウト、エラー変換、再試行方針を統一する。生の例外や内部パスを利用者に漏らさない。
- 音声解析・動画出力などの重い処理はリクエストやUI操作から分離する。ジョブID、待機・実行中・成功・失敗・中止、進捗、結果を管理する。
- 再起動時の中断ジョブと一時ファイルの扱いを定め、途中状態を成功扱いしない。
- 進捗通知はポーリング、SSE、WebSocket等から必要性に応じて選ぶ。切断・再接続・画面再読込後の状態照会を設計する。
- ブラウザから任意のPC内パスを自由に読めると仮定しない。ファイル選択による取込と、バックエンドが管理する素材参照を区別する。
- HTTP越しのファイル配信ではシークに必要な配信方式を確認し、大容量ファイルの全量メモリ保持を避ける。

## 10. セキュリティ・データ保護

- ローカルAPIは原則としてループバックに限定する。CORSは必要なOriginに絞る。CORSだけで認証やアクセス制御を代替しない。
- ローカルでも第三者サイトからの書き込みや任意ファイル操作を防ぐ。配信方式に合った認可・Origin/Host検証・CSRF対策などを選び、設計を記録する。
- フロントエンドへ埋め込まれる環境変数や配布JavaScriptにシークレットを置かない。秘密情報をログ、画面、ソースマップ、ZIPへ含めない。
- 外部の文字列をHTMLとして直接描画しない。必要時は用途を限定し、サニタイズ方針を定める。
- ファイル形式、サイズ、保存先、正規化後のパスをサーバー側で検証する。パストラバーサルやユーザー指定パスへの無制限アクセスを防ぐ。
- FFmpeg等の外部コマンドは引数配列で実行し、利用者入力をシェルコマンドへ連結しない。
- 元音源・歌詞・背景を編集結果で上書きしない。削除・置換・DB移行では復旧手段を用意する。
- 外部送信や自動投稿は明示的に認められた範囲で実施する。投稿済み記録と外部サービス上の公開状態を混同しない。

## 11. 性能とリソース管理

- 大量一覧、長時間音源、複数書き出しを想定して性能目標と計測条件を定める。
- 重い計算をUIのメインスレッドに集中させず、必要に応じてWorkerやPythonへ移す。
- 波形・画像・解析結果のキャッシュは上限と無効化条件を定める。
- 高頻度の再生時刻更新で画面全体を再描画しない。必要に応じて描画範囲を局所化する。
- Blob URL、AudioContext、イベントリスナー、タイマー、通信、プロセスなどを適切に解放する。
- 性能改善は可能な限り変更前後を同じ条件で測定する。推測だけで高速化済みと報告しない。

## 12. テスト方針

変更の影響とリスクに応じて検証を選ぶ。低影響の見た目変更に実装をなぞるテストを大量追加せず、実害のある失敗を検出する。

| 層 | 検証対象 | ツール例 |
| --- | --- | --- |
| 静的検査 | 型、Hooks、未使用コード等 | TypeScript、ESLint |
| 単体 | 時間計算、入力検証、状態遷移 | Vitest等 |
| UI結合 | 操作、保存、エラー・読込表示 | React Testing Library等 |
| API・Python | 契約、異常系、ジョブ、永続化 | pytest等 |
| E2E | 主要利用フロー、再読込復元 | Playwright等 |
| 実出力 | 動画・音声・字幕の内容 | FFprobe、再生・目視・聴取 |

- 正常系に加え、空データ、不正入力、ファイル不在、日本語パス、通信断、連打、キャンセル、保存失敗を影響範囲で確認する。
- 非同期テストは固定sleepを乱用せず、状態や要素の成立を待つ。
- APIモックの成功と実バックエンド接続の成功を区別する。
- 対象ブラウザで主要操作、キーボード、レイアウト、コンソール・通信エラーを確認する。
- テストを通すためだけに重要な検証を削除・無効化しない。既存失敗と今回の回帰を分けて記録する。
- 実行コマンド、環境、件数、成否、未実施理由を記録する。スクリーンショットだけで保存・出力の正しさを主張しない。

## 13. 独立レビューと完了条件

Reviewerは要件、実コード、差分、再現手順、検証ログを直接確認する。必要に応じて再実行し、Developerの自己評価だけで合格としない。

重大度はCritical / High / Medium / Lowとする。Critical・Highは修正・再検証を原則必須とし、残る場合は完成扱いにしない。既存REVIEWER.mdの例外運用を適用する場合も、ユーザーの明示判断と残存リスクを記録する。

完了時には以下を確認する。

- [ ] 受け入れ条件を満たし、主要フローが実データで動く。
- [ ] 対象変更に必要な型検査・lint・テスト・ビルドが成功している。
- [ ] 保存・復元・例外・キャンセルが必要範囲で検証されている。
- [ ] 無関係な変更、重大な回帰、秘密情報の混入がない。
- [ ] Reviewerの重大指摘が解消されている。
- [ ] 起動・終了・依存関係・データ保存先・復旧方法が記載されている。
- [ ] 未検証事項と既知の制約が明示されている。

検証不足はNOT VERIFIEDなどで示し、PASSや動作保証に置き換えない。

## 14. Shorts・音楽編集アプリ向け追加規約

### 14.1 データと編集

- 楽曲、Shorts編集プロジェクト、書き出しジョブ、投稿記録を別の識別可能なデータとして扱う。1曲から複数Shortsを作成可能な構造にする。
- 編集は非破壊とし、元音源・元歌詞と編集後の設定を分離する。
- 時刻の正本は整数ミリ秒などに統一する。API・保存形式・UI表示・FFmpegへの変換を明記し、浮動小数の累積誤差を避ける。
- 区間は開始を含み終了を含まない等の規則を定め、0以上・開始＜終了・終了≦素材長を検証する。
- 切り出し後の字幕は、元の時刻から開始時刻を引き、切り出し区間と交差する部分へ制限する。区間外や長さ0の字幕は除外する。
- 字幕のオフセット適用順序、重なりの許可、最小表示時間を仕様として定める。
- 例：42秒開始のShortsで元字幕43〜46秒は1〜4秒となる。境界字幕・負オフセットもテストする。
- 編集の自動保存と復元、素材移動時の再関連付け、必要なUndo/Redo範囲を定める。

### 14.2 プレビューと出力

- 音声の再生時刻を同期の基準にし、独立タイマーの加算だけで字幕位置を決めない。シーク、ループ、一時停止、曲切替を検証する。
- プレビューと書き出しで、時間軸・座標系・背景の拡大方式・文字の折返し・フォント・演出設定を共通仕様にする。
- 実装方式が異なる場合は代表フレームを比較し、許容差を定める。プレビューと完全一致すると未検証で宣言しない。
- 9:16・1080×1920などの出力プロファイルは設定として管理する。既存横動画コードの定数だけを変更して互換性を判断しない。
- FPS、音声、縦横比、回転情報、出力時間、字幕の表示を実ファイルで確認する。GPUエンコーダは利用可否を検出し、代替方式と速度差を明示する。
- FFmpegの終了コードだけで完成とせず、出力の存在・読込・時間・ストリーム構成を確認する。中止・失敗時の不完全ファイルを完成品として表示しない。
- UIの重なりガイドは目安とし、サービス・端末・表示条件で変わることを前提に調整可能にする。
- 「書き出し済み」「投稿予定」「投稿済み」は別状態とし、自動で同一視しない。

## 15. 納品と日本語の最終報告

納品物はソース、ロックファイル、README、設定例、必要なテスト、変更履歴、検証結果を含める。複数ファイルのアプリは原則ZIPとし、秘密情報、個人素材、node_modules、仮想環境、不要な一時出力を除外する。配布ビルドを含めるかは実行方式に応じて決める。

最終報告は次を簡潔に示す。

1. 実施内容と達成状況。
2. 主な変更と理由。
3. 実行した確認・テストと結果。
4. Reviewerの判定、指摘、対応状況、独立性の制約。
5. 未検証事項、残存リスク、既知の制約。
6. 成果物、起動・終了・利用手順。

本規約の作成のみを依頼された場合は、アプリ実装や動作試験まで実施済みと報告しない。
